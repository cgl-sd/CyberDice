# 1. 项目概述

**目标：**开发一款运行在小米手环 9 Pro 上的轻量摇骰子应用。用户通过自然摇腕动作触发掷骰，应用在本地生成结果，以动画与震动反馈完成一次 2～5 秒的闭环交互。

> **产品原则**  
> 不是“把手机骰子缩小到手环”，而是利用手环一直佩戴、抬腕即用、可感知手腕动作、可震动的特性，把“拿起骰子并掷出”的物理动作映射到数字骰子。

| **维度** | **v1.0 决策**                             |
|----------|-------------------------------------------|
| 首要设备 | 小米手环 9 Pro                            |
| 屏幕基线 | 336×480，矩形屏                           |
| 运行方式 | 完全本地，不依赖网络、手机桥接或 BLE      |
| 核心输入 | 加速度计摇腕；屏幕点击作为兜底触发        |
| 核心输出 | 骰子点数、滚动动画、短震动                |
| P0 模式  | 1D6、2D6、1D20                            |
| 开发环境 | macOS + AIoT-IDE + Vela JS                |
| 发布形态 | RPK；正式发布按小米 Vela 当前协作发布流程 |

# 2. 产品范围与版本边界

## 2.1 v1.0（P0）范围

- 启动后默认进入 1D6 主界面；用户无需登录、联网或初始化。

- 支持 1D6、2D6、1D20 三种模式切换。

- 支持“摇腕触发掷骰”；当传感器不可用或用户不便摇腕时，可点击主区域触发。

- 掷骰时播放 0.4～0.9 秒的快速滚动动画；停止后显示最终结果。

- 结果锁定时触发一次基础短震动。

- 避免误触发、连续抖动重复出结果，并提供合理冷却时间。

- 应用离开前台时取消加速度计订阅，重新进入前台时恢复，避免不必要的资源消耗。

- 所有核心功能在小米手环 9 Pro 真机上完成验收。

## 2.2 v1.1（P1）候选

- D4 / D8 / D10 / D12 / D100 等更多桌游骰。

- 大话骰（5D6）模式。

- 最近 10～20 次结果历史（若存储能力与体验验证通过）。

- 摇动灵敏度三档设置。

- 声音或更丰富的触觉反馈（仅在目标设备开放相应能力时评估）。

## 2.3 明确不做（v1.0）

- 联网、账号、云同步、排行榜。

- BLE 连接电脑或手机自定义协议。

- 广告、支付、订阅。

- 复杂 3D 物理模拟。

- 依赖气压计的玩法（9 Pro 虽支持压力传感器，但与首版核心体验无关）。

- 手环 10、手环 9、Watch 系列的发布阻塞适配。

# 7. 交互与界面设计

## 7.1 主流程

```text
打开应用
↓
1D6 主界面（READY）
↓ 摇腕 / 点击
SHAKING：骰面快速滚动
↓ 检测停止
SETTLING：短暂收束
↓
RESULT：显示最终结果 + 短震
↓ 冷却结束
READY：可再次掷骰
```

## 7.2 页面布局建议（336×480）

| **区域**     | **建议**                        | **说明**                                       |
|--------------|---------------------------------|------------------------------------------------|
| 顶部 10～15% | 模式标签：1D6 / 2D6 / D20       | 轻量，不抢占主结果。                           |
| 中部 55～65% | 大号骰面/数字                   | 应用视觉焦点。1D6 用点阵骰面，D20 可用大数字。 |
| 结果辅助区   | 2D6 显示“3 + 5 = 8”             | 不只显示总和，避免用户怀疑。                   |
| 底部 15～20% | “摇腕或点击”提示 + 模式切换入口 | 交互提示保持简短。                             |

## 7.3 交互细节

- 主骰子区域同时是最大的点击热区，避免小屏幕精准点击。

- 模式切换不应在摇动过程中生效；若用户在 SHAKING 状态切换，则延迟到本次结果完成后或直接禁止交互。

- 结果出现后至少保留 1 秒稳定显示，避免用户看不清。

- 动画只服务于“掷骰感”，不追求复杂 3D；优先保证帧率与响应。

- 颜色与装饰不作为理解结果的唯一手段；最终数值必须直接显示。

# 9. 状态机设计

| **状态**     | **进入条件**             | **行为**                                     | **退出条件**                |
|--------------|--------------------------|----------------------------------------------|-----------------------------|
| READY        | 页面可用/冷却结束        | 等待摇腕或点击                               | 有效触发                    |
| SHAKING      | 检测到连续运动或点击触发 | 播放快速骰面变化；记录运动强度               | 摇动停止 / 点击动画时间满足 |
| SETTLING     | 运动强度回落             | 等待 250～450ms 去抖；停止接收新的 roll 触发 | 稳定窗口满足                |
| RESULT       | 生成最终结果             | 显示结果；震动一次；开始冷却                 | 冷却 500～800ms 后          |
| ERROR_SENSOR | 传感器订阅失败           | 提示可点击掷骰；保持其他功能可用             | 重试成功或页面结束          |

# 10. 摇动识别算法

**原则：**加速度计只负责判断“是否发生一次明确摇动”，不参与随机结果计算。这样既能避免偏置，也便于单元测试。

## 10.1 采样

- 调用 `sensor.subscribeAccelerometer({ interval: "game", ... })`，目标约 20ms/次。

- 每个样本记录时间戳 t 与 x/y/z。

- 页面隐藏或销毁时立即 `unsubscribeAccelerometer()`。

## 10.2 特征

```text
m(t) = sqrt(x² + y² + z²)
d(t) = |m(t) - baseline|
jerk(t) = |m(t) - m(t-1)| / Δt
```

baseline 不建议在设计阶段硬编码成固定单位值；以真机样本估计静止基线和噪声。若真机输出确认采用标准重力相关单位，可再使用约 1g 附近作为参考。

## 10.3 首版检测策略

1. 在 READY 中，短窗口（例如 250ms）内出现至少 2～3 个超过 EnterThreshold 的峰值，进入 SHAKING。

2. SHAKING 中持续刷新最后一次显著运动时间 lastMotionAt。

3. 若连续 300～450ms 未出现显著运动，进入 SETTLING。

4. SETTLING 再等待约 150～250ms；若重新出现强运动，则回到 SHAKING；否则生成结果。

5. 生成结果后进入 500～800ms COOLDOWN（可并入 RESULT），期间忽略新的传感器触发。

> **阈值调参方式**  
> 不要先追求“数学上漂亮的阈值”。在 9 Pro 真机采集至少三类动作：静止/抬腕查看、正常走路、主动摇骰。用日志比较峰值与窗口特征，再确定 EnterThreshold、StopThreshold、窗口长度。首版验收看真实误触/漏触，不以某个固定数值为目标。

# 11. 随机与骰子规则

| **模式** | **生成规则**                   | **显示**                      |
|----------|--------------------------------|-------------------------------|
| 1D6      | 独立生成 1～6                  | 传统六面骰点阵 + 数字（可选） |
| 2D6      | 独立生成两个 1～6，total = a+b | 两个骰面 + “a + b = total”    |
| 1D20     | 生成 1～20                     | 大号数字；可辅以 D20 标签     |

- 使用平台可用的伪随机函数生成结果；每次掷骰结果与前一次、摇动方向、摇动强度独立。

- 2D6 必须分别生成两个独立 D6，不能直接生成 2～12 的均匀随机数；否则概率分布错误。

- 结果生成只发生一次，动画中间数字不能被误认为最终随机抽样次数。

# 14. 异常与降级策略

| **场景**           | **处理**                                       | **用户影响**                 |
|--------------------|------------------------------------------------|------------------------------|
| 加速度计订阅失败   | 记录错误；页面进入点击可用模式；提供简短提示   | 仍可点击掷骰，不崩溃         |
| 震动调用失败       | 吞掉平台异常并继续显示结果                     | 仅缺少触觉反馈               |
| 传感器长时间无数据 | 尝试在页面重新激活时重订阅；保持点击兜底       | 摇腕可能不可用，但主功能可用 |
| 快速连续点击       | Controller 层冷却/防重入                       | 一次完整流程后才允许下一次   |
| 模式切换中触发     | 以切换完成后的当前 mode 为准；禁止并发状态写入 | 结果格式一致                 |
| 页面离开/恢复      | stop/start 传感器；重置 Detector 临时状态      | 无幽灵触发                   |

# 15. 调试日志与可观测性

- DEBUG 构建允许输出：采样频率、magnitude、peak count、state transition、trigger source。

- RELEASE 构建不持续输出高频 sensor sample，避免性能与日志噪声。

- 真机调参阶段提供可切换的“诊断模式”：每 100～200ms 聚合输出一次指标，而不是每 20ms 打一行。

- 关键错误至少记录：sensor subscribe fail code、vibrate fail、unexpected state transition。

# 19. Sprint 0：第一天就应该验证的事情

1. 在 Mac 安装 AIoT-IDE，创建 Watch/Vela JS 最小项目并在模拟器运行。

2. 创建/设置 336×480 的 9 Pro 目标布局，确认页面比例正常。

3. 生成 debug RPK。

4. 确认你能获得支持“第三方应用安装”的测试版小米运动健康或对应合作渠道。

5. 把 RPK 实际安装到小米手环 9 Pro。

6. 在真机上调用 `subscribeAccelerometer`，输出低频聚合日志；确认摇手时 x/y/z 明显变化。

7. 调用 `vibrator.vibrate`，确认设备可感知震动。

8. 只有 5～7 全部完成，才开始正式开发摇骰子 UI 与算法。
